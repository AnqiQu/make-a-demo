MakeADemo codebase guide

How a repo turns into a short demo video

MakeADemo is a Bun/TypeScript product that generates short demo videos from runnable web apps, codebase context, and product descriptions. This page is a local, static walkthrough of the whole codebase: the user-facing intake, the API and queue, the pipeline gates, the sandbox boundary, capture, compositing, and final delivery.

Background

The system before you follow any file

Think of MakeADemo as a compiler for demos. The input is a maker's project plus their intent; the output is a final video. The product is intentionally organized around the MakeADemo Pipeline, because every stage has a different trust level and a different external seam.

The durable pipeline order: Context Gathering → Repo Security Screen → Repo Preparation → Script Generation → Capture Path Validation → Footage Capture → Compositing → final output.
Context Gathering Security Screen Preparation Script Validation Capture Composite Output

Beginner mental model

A submitted repo is not trusted just because an agent prepared it. MakeADemo separates the powerful preparation workspace from the locked-down app runtime, then proves the generated browser path in a deterministic validation pass before recording final footage.

The key artifact handoff

Repo Preparation produces a Preparation Manifest. Script Generation produces a Demo Script candidate. That candidate only becomes an AcceptedDemoScript after Capture Path Validation succeeds.

The external seams

The repository keeps infrastructure behind seams: Neon for persistence, R2 for storage, Daytona for sandboxes, Playwright for browser automation, Remotion for rendering, and Resend for final video notification email.

Intuition

Why the code is shaped this way

The central design pressure is simple: MakeADemo needs enough agency to prepare unknown apps, but enough determinism to trust the footage it ships. The codebase therefore reads like a sequence of gates, not like one giant script.

Powerful side

Preparation agent can inspect, edit, and install dependencies in an ephemeral workspace.

execute syncSubmittedCodeWorkspace dependency install window

Trusted side

Submitted app runtime is sealed, validated, captured, and rendered through explicit contracts.

executeSubmittedCode Runtime Network Lockdown AcceptedDemoScript
Concrete toy example: if a generated script says “click Sign in, then wait for dashboard,” validation dry-runs that path before capture. If the app tries to call an outside API after the dependency-install-only window, the network attempt is sanitized and treated as boundary evidence rather than silently tolerated.

Code

A high-level walkthrough of the repository

Follow the product from the browser inward. Each expandable section names the public seam or orchestrator that matters most, then points to the files worth reading next.

1. Frontend intake: collect enough context to queue work

src/app/main.tsx renders ContextGatheringApp. That app coordinates RepoConnectionFields and ContextDetailsForm, then moves the maker's details through collectIntakeDetails, startContextGatheringSubmission, and submitIntake. 

Browser
  src/app/main.tsx
    → ContextGatheringApp
      → RepoConnectionFields
      → ContextDetailsForm
      → submitIntake()
2. API and persistence: uploads plus durable queue records

src/server/api/server.mts calls createApiApp from src/server/api/app.ts. The relevant routes are POST /api/uploads and POST /api/context-gathering/submit. The submit route calls submitContextGathering, which calls ContextGatheringStore.createQueuedProject.

The Neon implementation, NeonContextGatheringStore.createQueuedProject, upserts users and creates queued projects plus linked demoRequests.

3. Worker and queue: claim the next project atomically

project-demo-generation-worker.mts calls processNextProjectDemoGenerationJob. NeonProjectDemoGenerationQueueStore.claimNextQueuedProject atomically claims queued projects and returns the input needed by runFullPipelineJob.

4. Orchestration: promote candidates only after validation

runPipelineJob handles screenRepoSecurity, prepareRepo, generateScriptPackage or generateDemoScriptPackage, and then runCapturePathValidation / validateCapturePath. A candidate becomes an AcceptedDemoScript only after validation succeeds. 

DemoScriptCandidate
  └─ validateCapturePath(...)
       ├─ parse Demo Script
       ├─ validate prepared runtime
       ├─ dry-run browser path
       └─ report boundary violations

success → AcceptedDemoScript
5. Runtime seam: agent power is not app runtime power

PreparationWorkspace exposes execute, executeSubmittedCode, setOutboundNetworkAccess, setSubmittedCodeNetworkAccess, and syncSubmittedCodeWorkspace. The Daytona provider, DaytonaSdkPreparationWorkspaceProvider, creates a parent agent sandbox and a submitted-code sandbox with networkBlockAll: true.

runDependencyInstallWithNetworkWindow opens the dependency-install-only network window and reseals it in finally.

6. Capture Path Validation: deterministic dry-run trust gate

validateCapturePath parses the Demo Script, runs assertDemoScriptCaptureSdkContract, then validates the project through validateProject. The implementation path includes DaytonaSandboxRunner.runValidation, PlaywrightBrowserValidator.validate, DefaultCapturePathSceneValidator.validateScene, findRuntimeBoundaryViolations, sanitizeNetworkAttempts, and sanitizeNetworkAttemptUrl.

7. Footage, compositing, storage, and notification

runFullPipelineJob handles persistence, captureCompositeAndReview, Footage Capture, Compositing, Draft Composite review, and the final result. Footage starts at captureScenesFromScript and records through PreparedWorkspacePlaywrightSceneRecorder, producing a CaptureManifest.

Compositing starts at compositeVideoFromScript and renders through RemotionVideoRenderer.renderVideo. Delivery is handled by storeAndLinkFinalVideo, R2FinalVideoStorage.storeFinalVideo, NeonDemoRequestFinalVideoStore.linkFinalVideo, finalVideoEmailsEnabled, and ResendFinalVideoEmailNotifier.sendFinalVideoReadyEmail.

Source-observed caveat: the current queued worker path appears not fully wired for complete full-pipeline output, because it does not appear to pass prepareFreshCaptureState or reviewDraftComposite. Treat this as a cautious reading of the source, not as a product guarantee.
